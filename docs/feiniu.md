# 飞牛影视接入

执行器为 `media.feiniu.Feiniu`，填写在 `Media.Executor`。
`Player.Executor` 继续使用 `player.pioneer.Pioneer` 或 `player.oppo.Oppo`。
实现基于飞牛影视 0.9.8-1 的实际接口和其网页客户端 631，其他版本需要验证。

## 配置

将 `config/feiniu.example.yaml` 的 Media 段放入现有 `config.yaml`，
填写飞牛影视账号和服务地址，并核对原有 `Player.MappingPath`。
飞牛返回的是 NAS 实际路径，例如 `/vol4/1000/tv`；
原来为 Emby 容器目录配置的 `/media` 映射可能需要改成这个实际路径。
本机先锋固件不能可靠地自动切换多个共享。NAS 现已将原目录整合到
`/vol1/1000/share`，并只导出这一个 NFS 共享；其下的 `movie`、`tv` 等九个子目录
与原目录为同一挂载位置。设置 `Player.UseNetShareLogin: false`，
在播放机上预先进入 `share`，再由路径映射选择其中的子目录。

例如飞牛文件位于 `/vol4/1000/tv/剧集/第1集.mkv`，
`Player.MappingPath` 可将 `Media: /vol4/1000/tv` 对应到
`NFS: /192.168.31.2/tv`。这表示同一个 `share` 内的 `tv` 子目录，
不要求先锋切换到另一个 NFS 共享。其余旧目录按相同方式映射。

Host 填影视独立服务根地址，例如 `http://192.168.1.10:8005`。
不要填写系统桌面端口 5666 或带 `/v` 的网页地址。
确认飞牛影视兼容接口已经启用且容器可以访问该服务。
密码必须是 YAML 字符串，纯数字密码也应加引号。

运行前核对 `Player.MappingPath` 的实际路径，重启程序后，
在选片客户端开始播放一个未排除格式的影片即可触发投送。

默认 `OnlyWhenPlayerOnline: true`，只有播放机控制端口可达时才查询飞牛影视。
先锋检查 TCP 8090，Oppo 检查 TCP 436，仅连接并关闭，不发送唤醒或播放指令。
离线期间不登录或查询飞牛影视，改为每 `OfflineCheckInterval` 秒检查播放机，
默认 5 秒；在线期间按 `PollInterval` 查询，默认 2 秒。
关机被检测到后清除记录基线，重新上线的首次查询只建立新基线，
不补播离线期间的历史变化。新查询和路径解析完成后也会再次检查在线状态，
避免在等待网络响应时关机却仍发出投送。

这是控制服务可达性检查，不是独立的电源状态接口。
如果待机时控制端口仍开放，将被视为在线；已经发出的 HTTP 请求不会强制中断。
第三方播放机执行器需提供返回 bool 的 `is_online()`；
先锋执行器使用已有的 `_is_port_open()`；
不支持时可设置 `OnlyWhenPlayerOnline: false` 使用持续轮询。
既有播放机自身的后台状态检查仍按原逻辑运行。

先锋回调实际确认开始播放后，自动标记该影片已观看，无需配置开关。
标记失败会记录错误，不中断播放；播放结束达到原有 70% 条件时可再次尝试。
不会将先锋进度写回飞牛播放记录，以免形成触发循环。
请求使用的网页客户端版本由适配器内部维护，无需在配置中填写。
实测 Solink 播放时，该先锋的 `Playback.GetPlayingStatus` 仍可能返回 `-1`；
此时开始播放回调不会触发，程序也不会仅凭 `Playback.PlayFile` 返回 `0` 标记已观看。

## 识别规则

- 使用当前账号的 `/v/api/v1/play/list`，默认每 2 秒查询一次。
- 启动、重新上线及查询失败后的第一次成功查询只建立基线，不投送历史记录。
- 新出现的正进度记录，或已有记录的进度、媒体版本变化，可以形成候选。
- 收藏、已观看状态、封面、标题变化均不作为播放动作；进度归零也不触发。
- 同一影片持续上报进度时只处理一次，不因超过重复检测时间再次投送。
- 同一影片停止进度变化至少 `ActivityIdleTimeout` 秒后，后续变化才可重新识别，
  同时受 `RepeatFilterTimeout` 限制。暂停后恢复也可能被视为新的活动。
- 多条影片同时形成候选时跳过该次不明确的选择；播放器忙碌时也跳过，不排队。
- 按记录中的 `media_guid` 精确匹配文件；找不到唯一版本时不随意选择第一个文件。
- `.iso` 按 ISO 转交，`BDMV/index.bdmv` 等规范化为原盘根目录；
  名字包含点号的原盘目录通过原生 `POST /server/path` 只读查询，
  核对所选版本目录中的 `BDMV/index.bdmv`，不依赖兼容接口的 Path / Container。
  此目录查询需要飞牛账号具有相应的浏览权限；查询失败时停止投送。
- 失败的启动不会标记已观看。失败的活动不会持续自动重试；
  停止客户端播放并等待上述空闲及重复检测时间后，重新播放可形成新候选。

## 已知限制

这是播放记录轮询，不是已验证的播放开始 WebSocket。
网页客户端首次记录延迟约 1 秒，之后每 15 秒更新；
实际联动延迟还取决于客户端上报、网络和先锋准备时间。
已存在记录在相同进度重新开始、且尚未产生不同记录时无法识别。
短时间内暂停、恢复、快进和重复点播也无法完全区分。
没有进度的直播记录不在本版支持范围内。

记录未提供明确的客户端来源，不能实现 Emby 的 `BlockDevices` 筛选。
建议选片使用专用飞牛账号，避免同账号其他客户端播放时触发先锋。
本版尚不能远程停止飞牛网页或 App 串流，选片客户端可能继续播放，
需要手动暂停或退出；这也影响同一影片下次活动的识别。
本版不把收藏或手动标记已观看当作快捷投送按钮。

当前每个实例只能选择一个 Media 执行器：切换此配置后该实例改为监听飞牛影视。
HTTP 请求有超时，认证过期会重登，轮询错误会退避并重新建立基线。
日志不记录密码、Token、请求认证头或服务端原始响应。
日志保存在配置目录的 `logs/blurayposter.log`，Docker 内为
`/config/logs/blurayposter.log`，每天轮转并保留 7 份历史日志；
控制台仍输出日志，可继续使用 `docker logs` 查看。
固件升级如改变接口或签名算法，需要重新核对适配。

以及配置目录日志、UTF-8 写入、日志级别和每日轮转。

只读验证读取 8 条播放记录，其中 2 条可精确解析 MKV 路径。
其中一次通过只读的 `POST /v/api/v1/item/list` 实际验证了 POST 请求体签名。
另 6 条记录的历史 `media_guid` 与当前文件列表不一致，按规则拒绝猜测路径。
这不能证明文件已被删除，可能与重新扫描或版本变化有关。
验证工具只调用读取方法，拦截写入及设备调用，不调用初始化或投送方法，
没有写入观看状态、安装代码或切换运行配置。

已观看写回的请求体来自当前网页调用，POST 签名用 JavaScript 参考向量及单元测试核对。
